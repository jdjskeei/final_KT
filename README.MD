# Ответы

## Задание 1

Это один и тот же процесс, а не две его копии. `pid namespace` позволяет ему иметь разные PID: внутри `web-42` он виден как PID 1, а в пространстве процессов хоста — как PID 48231.

При этом процесс может находиться в namespace контейнера и одновременно управляться systemd как часть сервиса. Противоречия нет: namespace определяет, какие PID видны процессу, а systemd отслеживает его и управляет им через хостовую систему и cgroups. Но само совпадение PID ещё не доказывает принадлежность к конкретному сервису — в лекции это часть условного примера. В обычном Docker-запуске приложение не обязательно будет `Main PID` отдельного systemd-юнита.

## Задание 2

Потому что контейнеры используют общее ядро, а системное время — общий ресурс хоста. Если дать одному контейнеру возможность менять часы через `date -s`, это затронет и остальные контейнеры.

Из-за резкого изменения времени могут ломаться таймеры и задачи по расписанию, возникать проблемы с сертификатами, проверкой срока действия токенов и порядком записей в логах. Поэтому Docker по умолчанию не даёт контейнеру `CAP_SYS_TIME`, даже если внутри него пользователь — root.

## Задание 3

Он останется в сетевом namespace хоста, то есть будет использовать те же сетевые интерфейсы, IP-адреса, маршруты и порты. Если на хосте nginx слушает `0.0.0.0:80`, внутри такого контейнера команда `ss -tlnp` тоже покажет этот слушающий сокет. Правда, имя процесса и его PID могут не отображаться из-за отдельного PID namespace.

В отличие от него, Docker обычно создаёт для `web-42` отдельный network namespace со своим сетевым стеком. Поэтому наш контейнер через `unshare` изолирован по процессам и hostname, но не по сети.

## Задание 4

Они решают разные задачи: Docker запускает контейнеры, systemd управляет сервисами, а Kubernetes управляет контейнеризированными приложениями на множестве машин. Но на нижнем уровне они опираются на механизмы одного и того же ядра Linux.

Например, Docker и systemd используют **cgroups** для учёта и ограничения ресурсов. Docker применяет **namespaces** для изоляции контейнеров, а Kubernetes через контейнерный runtime использует их для запуска контейнеров в Pod. Также применяются capabilities и другие механизмы безопасности.

Получается, это разные инструменты поверх общих примитивов ядра Linux, а не три полностью независимых способа управлять процессами.
